# Build-Kit Agent Learnings

- Routes in this project use raw `knex` queries directly against Postgres (see any existing `routes.ts` in a slice folder) — not the `supabase`/`readmodel` helper shown in the generic skill SKILL.md templates. When an existing `routes.ts` pattern differs from a skill's example, follow the existing codebase pattern.
- Migrations live at repo root `migrations/V{n}__*.sql` (not `supabase/migrations/` as some skill templates say). Append-only — never edit an existing migration file, add a new `V{n}` file instead.
- `.build-kit/.eventmodelers/config.json` is absent in this repo (only `install-manifest.json` exists under `.build-kit/.eventmodelers/`) — board sync / `update-slice-status` / MCP calls are skipped; slice status is tracked locally in `.build-kit/.slices/<context>/index.json` only.
- No `.githooks` are installed in this repo (no `core.hooksPath`, no `.githooks/` dir) — the commit-scope guard (`npm run run:checks`) is not auto-invoked by git. Always run `npm run run:checks -- --staged` manually right after staging (and before committing) a slice's files, since nothing else will catch a scope violation.
- `npm run run:checks` with no flag checks ALL uncommitted changes (staged + unstaged + untracked) in the whole working tree, not just this slice — if the working tree has unrelated pre-existing modifications from another task, use `-- --staged` after staging only the intended files, or the check will report unrelated violations.
- A "Planned" slice that already has a full-looking implementation may just have a field renamed in slice.json (e.g. a readmodel/screen field renamed while the underlying event field is untouched) — diff every `fields[]` entry against the actual TS types/column names rather than assuming the existing code is already correct just because it runs and passes tests.
- Inside one slice.json, `storylines[]` walkthrough field-name examples can lag behind a field rename and disagree with each other — the canonical source of a field's current name is the node's own top-level `fields[]` array (on `readmodels`/`screens`/`commands`), not the storyline examples.
- `server.ts` auto-discovers every `src/slices/**/routes{,-*}.ts` (and `src/common/routes.ts`) via glob and calls its exported `api()` — a new slice's `routes.ts` needs no manual import/wiring anywhere.
- `.build-kit/lib/checks/10-slice-scope.cjs` only allows `migrations/V*.sql`, `src/slices/{context}/{slice}/**`, `src/slices/{context}/{Context}Events.ts`, and `src/common/loadPostgresEventstore.ts` in one commit — anything under `.build-kit/.slices/**` (e.g. `index.json` status changes) fails that check if staged alongside slice code. Commit the slice implementation first, then a separate follow-up commit for the `index.json` status flip (matches the existing `feat: ...` / `chore: mark ... Done` commit pairing already in this repo's history).
- A readmodel's own `dependencies[]` INBOUND list in slice.json is the authoritative source for which events its projection should handle — don't assume a projection needs every event a sibling read model in the same context reacts to (e.g. one read model may intentionally omit a cancellation event that another one handles).
- The generic Ralph instruction to run a "test-analyzer" skill for a `code-slice.json` file doesn't apply to this project — no such skill exists under `.claude/skills/`; skip that step silently rather than erroring.
